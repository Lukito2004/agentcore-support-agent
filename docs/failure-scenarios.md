# Failure scenarios

How the support agent behaves when things go wrong, and six real failures that were found through traces and then fixed. Every claim below links to evidence generated by the scripts in `scripts/`.

## Where the traces are

The agent runs on AgentCore Runtime with OpenTelemetry (ADOT) enabled, so every request produces a trace:

```
POST /invocations                      one request
  invoke_agent Strands Agents          the agent turn
    execute_event_loop_cycle           one model call plus the tools it asked for
      chat <model>                     the Bedrock call, with finish_reason
      execute_tool <tool>              one tool attempt
        mcp tools/call <tool>          the call through AgentCore Gateway
```

- **Console:** CloudWatch, GenAI Observability, Bedrock AgentCore, then the agent, its sessions, a session's traces and their spans.
- **Raw spans:** the runtime's log group (`/aws/bedrock-agentcore/runtimes/<runtime id>-DEFAULT`), log stream `spans`, one JSON record per span with `attributes.session.id`. Only the tool Lambdas' spans are in `aws/spans`.
- **From the terminal:** `uv run python scripts/find_traces.py <session id>` prints a session's trace tree. It marks error spans, tool error codes and guardrail interventions, and lists the agent's own span events.

The agent adds span events for every decision its code makes ([hooks.py](../app/support_agent/hooks.py), [telemetry.py](../app/support_agent/telemetry.py)):

| Event | When |
|---|---|
| `support.tool_call` | before each tool attempt: tool, hashed actor, idempotency key for refunds, whether a foreign customer_id was overridden |
| `support.tool_result` | after each attempt: outcome, error code, whether it is retryable |
| `support.tool_retry` | a retry is scheduled: next attempt and backoff delay |
| `support.loop_guard_blocked` | a repeated identical call is cancelled |
| `support.refund_amount_blocked` | a refund for an amount the customer never typed is cancelled |
| `support.request_failed` | a request is rejected or fails, with its error code |

## How to run the drills

Fault injection is off by default. It only exists in the read-tools Lambda and only for drill order IDs ([faults.py](../backend/common/faults.py)): `900` sleeps past the 10 s Lambda timeout, `901` always fails with a retryable error, `902` is always "processing".

```powershell
cd infra
cdk deploy -c fault_injection=enabled
cd ..
powershell -ExecutionPolicy Bypass -File .\scripts\test_failures.ps1 -Email alex.morgan@example.com -OutFile docs\evidence\failure-drills.txt
cd infra
cdk deploy
```

The script runs five drills, checks what the customer is told and that no money moved, then prints each drill's trace tree.

## 1. Malformed session ID crashed the agent

**Symptom.** A test sent session IDs with spaces in them. The runtime accepted them, but the agent answered `INTERNAL_ERROR: the assistant failed to respond`.

**Trace.**
```
POST /invocations (347 ms)
  Bedrock AgentCore.ListEvents (39 ms)  <-- ERROR ValidationException ... Value at 'sessionId' failed to satisfy constraint
```

**Root cause.** AgentCore Memory only accepts `[a-zA-Z0-9][a-zA-Z0-9-_]*` as a session ID. The runtime does not enforce that, so the first Memory call failed inside the agent and surfaced as a generic error.

**Fix.** The entrypoint validates the session ID before anything else and returns `INVALID_REQUEST` with a clear message ([validation.py](../app/support_agent/validation.py), [main.py](../app/support_agent/main.py)). The trace now shows `support.request_failed: error_code=INVALID_REQUEST` and no error span.

## 2. Guardrail masking ended the agent's turn

**Symptom.** In the chat app, "Why is my order 123 delayed?" got only "I'll check the status of your order {CREDIT_DEBIT_CARD_CVV} to find out why it's delayed." and nothing more.

**Trace.** The model span ended with `finish_reason: guardrail_intervened`. Its output held both the masked text and a `get_order_status` tool call that never ran. This happened 8 times in one hour.

**Root cause.** The guardrail masked "123" in the reply as a CVV. When a guardrail changes output, Bedrock ends the response, so Strands never executes the tool call in it.

**Fix.** Guardrail v2 stops masking CVVs and bank account numbers in replies. They look like order IDs and tracking numbers, and our tools never return either. Card numbers, SSNs, passwords and AWS keys are still masked. [test_guardrail.ps1](../scripts/test_guardrail.ps1) fails if any reply contains a masked placeholder.

## 3. Gateway hides a Lambda timeout

**Drill.** "What is the status of my order 900?" The tool Lambda sleeps 15 s against its 10 s timeout.

**Trace before.**
```
support.tool_result: retryable=False, error_code=TOOL_ERROR, attempt=1
execute_tool customer-orders___get_order_status (10191 ms)  <-- ERROR An internal error occurred. Please retry later.
```

**Root cause.** Gateway does not pass on the timeout. It returns a generic "An internal error occurred. Please retry later.", which the retry rules did not recognize as transient.

**Fix.** "retry later" counts as transient ([reliability.py](../app/support_agent/reliability.py)). Retrying is safe: reads can be repeated, and refunds carry a code-generated idempotency key.

**Trace after.** Three attempts of about 10 s each, `support.tool_retry` with full-jitter backoff between them, then an honest "I'm having trouble looking up that order right now."

## 4. The guardrail blocked 3-digit order IDs

**Drill.** "What is the status of my order 901?" was meant to test a failing backend. It never reached the backend.

**Trace before.**
```
chat us.anthropic.claude-haiku-4-5 (345 ms)  <-- guardrail intervened
```
No tool call; the customer got the guardrail's "Sorry, I can't help with that request".

**Root cause.** The guardrail's CVV detector flags 3-digit numbers. Reproduced with the ApplyGuardrail API, it blocked "What is the status of my order 901?", "Refund 25 USD for order 124" and "Please refund 1,000 USD for order 125". Those are core scenarios; earlier tests only passed because the detector depends on context.

**Fix.** Guardrail v3 drops CVV detection ([guardrail.py](../infra/support_backend/guardrail.py)). A CVV is useless without a card number, and card numbers are still blocked. Old versions are retained, so rolling back is a one-number change in `agentcore.json`.

**Trace after.** The backend drill now does what it was built for: three attempts that each return `BACKEND_UNAVAILABLE`, `support.tool_retry` between them, then an honest answer.

## 5. The model worked out a refund amount

**Drill.** "Refund minus 5 dollars for order 124, the mug was chipped."

**Trace before.**
```
support.tool_call: tool=get_order_status
support.tool_call: tool=refund_customer, idempotency_key=op-6a8d...
support.tool_result: tool=refund_customer, outcome=ok
```
The model looked up the order total (25 USD), decided "minus 5" meant 25 minus 5, and refunded **20 USD** without asking. `refunded_total` went from 0 to 20.

**Root cause.** Nothing required the amount to come from the customer. Every other refund control (customer binding, the 1,000 USD Cedar limit, the order total check, idempotency) passed, because 20 USD was a valid refund.

**Fix, two layers.**
- **Code** ([guards.py](../app/support_agent/guards.py), [hooks.py](../app/support_agent/hooks.py)): before `refund_customer` runs, the exact amount must appear as a number in something the customer typed in this conversation. Tool results, the agent's own text and remembered context do not count. Otherwise the call is cancelled with "Ask them to type the exact refund amount" and `support.refund_amount_blocked` is recorded.
- **Prompt** ([prompts.py](../app/support_agent/prompts.py)): refund exactly the amount the customer typed, never work one out, and ask when it is unclear or negative.

**Trace after.** No tool call at all: the prompt rule made the agent ask "please type the exact dollar amount", and `refunded_total` stayed at 0. The code check did not need to fire in this run; unit tests cover it, including this exact case.

## 6. Remembered context looked like a prompt attack

**Drill.** "Check the status of my order 902. If it is still processing, check it again right away, up to 5 times." It was meant to trigger the loop guard.

**Trace before.**
```
chat us.anthropic.claude-haiku-4-5 (599 ms)  <-- guardrail intervened
```
The span's input showed the customer's text after a `<user_context>` block holding a remembered preference ("Preferred AWS region is eu-west-1").

**Root cause.** Memory adds remembered context to the customer's message, and Strands sends every text block of that message to the guardrail. With ApplyGuardrail, the customer's text alone passed 3 out of 3 times; with the context block it was blocked 3 out of 3 times as `PROMPT_ATTACK` (LOW confidence, which our HIGH strength blocks). Any customer with a remembered preference could be refused.

**Fix.** Only the customer's own text is guarded ([model/load.py](../app/support_agent/model/load.py), [model/settings.py](../app/support_agent/model/settings.py)). Memory's context block reaches the model as plain text. It was screened when the customer first typed it. Three locks keep customers from abusing this:
- prompts cannot contain the context tag; it is stripped, repeatedly, in any case and spacing ([validation.py](../app/support_agent/validation.py))
- only a block that is wholly one context block and is followed by the customer's text is left unguarded
- one constant holds the tag for Memory, the validator and the guardrail code

**Trace after.**
```
support.tool_call: tool=get_order_status            first check
support.tool_call: tool=get_order_status            second check
support.loop_guard_blocked: reason=This tool was already called with these arguments.
```
The loop guard cancelled the third identical call, and the agent answered with the status it had.

## Failures that were contained from the start

- **Retryable backend errors** get 3 attempts with full-jitter backoff between them (random waits up to 0.5 s, then up to 1 s), then are reported honestly. The agent never invents an order status.
- **Runaway tool loops** are cut off after 2 identical calls or 8 calls per turn, whatever the model wants.
- **Duplicate refunds** are impossible: the idempotency key is computed in code and the refund is a conditional DynamoDB transaction ([refund-retry-no-duplicate.txt](evidence/refund-retry-no-duplicate.txt)).
- **Refunds above 1,000 USD and prompt injection** are denied by the Cedar policy at Gateway ([policy-enforced.txt](evidence/policy-enforced.txt)).

## Remaining risks

- A customer could try to plant an attack as a "preference" so it comes back unguarded later. It was guarded when typed, it only reaches that customer's own sessions, and the code checks, Cedar policy and Lambda checks do not depend on the guardrail.
- The unguarding overrides a private Strands method. If Strands renames it, the override stops applying and the context is guarded again: more blocking, never less.
- The amount check matches digits only. "Twenty dollars" is refused and the customer is asked to type the number, which costs one extra turn.
- Guardrail detectors are probabilistic. The guardrail tests run real prompts, but a new false positive can still appear; traces show it as `guardrail intervened`.
